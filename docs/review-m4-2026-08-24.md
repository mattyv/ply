# Adversarial review — M4 (2520f8b + a8834ad), 2026-08-24

Scope: the M4 fuzz/test/mutate tier as landed in `2520f8b` and confirmed in `a8834ad`,
reviewed against The-Ply-Spec.md (§1, §5.4b, §5.4c, §6, §8, §10, D6, D7, D12),
docs/m4-findings.md, docs/m3-slice-findings.md, and tests/spike/mutants/MUTANTS-FINDINGS.md.
Method: full read of the diff and every new module; independent verification of the
cargo-mutants claims against the installed 27.1.0 source; one deliberate self-mutation
run red-then-green; and five live probe fixtures run through the real
`cargo-ply verify` binary (details inline). The prose-only correction commit `9f5b1c7`
was read and is not reviewed.

**Bottom line first**: the milestone's core claim holds — a genuinely Kani-excluded
shape earns real fuzz evidence, and I verified the hard half myself (a seeded
`BTreeSet<u8>` bug is caught, shrunk to `[3]`, and reported as a witness-only
violation). The `--copy-target` spec falsification is real and correctly amended.
But the fuzz/test adapter **fails open on harness build errors** — a user's ill-typed
`examples` entry earns `fuzzed(256)` with zero diagnostics — which is the same
fail-open class the session's own findings celebrated fixing at the parser level,
recurring one level up. That is the most serious finding.

## Defects (wrong)

### D1 — SEVERE: a harness that fails to *compile* is reported as a clean pass

**Claimed**: `fuzzed(n)` means "proptest harness, n cases" (§5.4c); the findings' own
finding 3 says a parser that "fails open (reports zero failures when it can't find
what it's looking for) is a defect".

**Actually true**: `engines::fuzz::run_harness_tests` computes `success` but
`verify::run_fuzz_and_test_checks` never reads it — it checks only `timed_out` and
`failed_tests`. A harness run that dies in `cargo test`'s *compile* step produces no
libtest `failures:` block, so `failed_tests` is empty and both the `fuzz` and `test`
checks classify as passed.

**How checked**: live probe. Copied the `strongspec` fixture and changed one
`examples` entry to the ill-typed `add_small(0, 0) == "zero"` (a perfectly plausible
user typo — §5.4a says examples are arbitrary Rust `==` expressions, so nothing
validates them before codegen). Real run:
`verdict: fuzzed(256), diagnostics: []`. The harness never compiled
(`error: could not compile`), zero tests ran, and the envelope is indistinguishable
from a genuine clean pass. Reproduced a second way (a stale `mod ply_generated_cex;`
declaration with the file deleted — E0583 in the *target* crate): same clean
`fuzzed(256)`.

**Consequences**: (a) any shape the fuzz codegen mis-generates for silently passes
instead of erroring — precisely the class of bug this milestone's new codegen could
contain; (b) the `btreeset` acceptance test's assertions (`fuzzed(256)` + zero
diagnostics + harness *dir* exists) cannot distinguish "256 cases ran" from "harness
never built", so the milestone's own headline e2e is weaker than its name (see O4);
(c) `tested` is likewise earned by examples that don't compile, inverting E0501's
"never a silently skipped example" promise for the type-error case.

**Cost to fix**: small and contained — one classification branch in
`run_fuzz_and_test_checks` (`!timed_out && failed_tests.is_empty() && !run.success`
⇒ `X0901` tool_error carrying the compile output, label `tool_error` for both
checks), plus a regression e2e with an ill-typed example. Not fixed here: it needs a
classification decision (tool error vs. a new E-code for bad examples) that is a
design call, not a mechanical one.

### D2 — counterexample `inputs` were mislabeled for any fn whose parameter order is not alphabetical — **fixed in this review**

**Claimed** (implicitly, §1/§8): the counterexample is the concrete failing input; feedback
quality is the whole point.

**Actually true**: `render_fuzz_violation` built the JSON `inputs` map by zipping
`cf.params` (declaration order) against `fields.values()` — a `BTreeMap` iterated in
*alphabetical key order*. For `fn zorder(z: u32, a: u32)` with true witness
`z=0, a=5`, the envelope reported `{"z": "5", "a": "0"}` — values swapped across
parameters. The rendered cex test was correct (it decodes by name); the JSON witness
— the agent-facing artifact §1 stakes the design on — lied. No fixture caught it:
`fuzzbug` has one parameter and `strongspec`'s `x, y` happen to be alphabetical.

**How checked**: live probe fixture with `(z, a)` parameter order and a bug seeded at
`a == 5`; observed the swap in real `--json` output, then the correct
`{"a": "5", "z": "0"}` after the fix.

**Fix applied (trivial, called out in the commit)**: both branches of
`render_fuzz_violation` now look fields up by parameter name. `cargo check
--workspace --tests` stays warning-clean; ply-cli unit tests, `fuzzbug` and
`strongspec` e2e re-run green; probe confirms correct output.

### D3 — the `>50% rejection` W0503 warning is mathematically unreachable on its ratio path

**Claimed** (m4-findings, TODO.md): "`requires` becomes a `TestCaseError::reject`,
counted so a >50% rejection rate can be flagged"; §5.4c requires "a warning when the
rejection rate is high".

**Actually true**: the generated test increments `__ply_total` on *every* closure
invocation — including the ones that are then rejected — so `tot = accepted + rej`,
and the guard `rej/(tot+rej) > 0.5` reduces to `rej > tot`, i.e. `accepted < 0`:
impossible. The only way W0503 ever fires is proptest's own global-reject *abort*
(a separate marker), which needs a rejection rate near 100%, not 50%.

**How checked**: arithmetic on the generated code in `fuzz_gen::generate_fuzz_test`,
then a live probe: `#[ply::requires(x > 12)]` under the biased-small strategy is
~57% rejection — real run produced `fuzzed(256)` with **zero** diagnostics. No test
in the suite exercises W0503's ratio path, so nothing caught this.

**Cost to fix**: one line in the codegen (don't count rejected invocations in
`__ply_total`, or compare `rej/tot`), plus a fixture at ~60% rejection.

### D4 — a fuzz run that executed approximately zero cases still earns `fuzzed(n)`

**Claimed**: `fuzzed(n)` = n cases ran (§5.4c's check→verdict table).

**Actually true**: when proptest aborts on too many global rejects, the generated
test *passes* (the abort arm only eprints a marker), and the adapter assigns the full
`fuzzed(n)` verdict with W0503 as a warning. Live probe:
`#[ply::requires(x > 20 && x < 24)]` (essentially nothing in the strategy satisfies
it) → `verdict: fuzzed(256)`, one W0503 (`abort:Too many global rejects`). The
verdict claims 256 cases of evidence; approximately none ran. A warning does not
license a verdict string that overstates the evidence — by the project's own D6
framing this should be a status/downgraded verdict, not `fuzzed(256)`.

**Cost to fix**: on the abort marker, emit a downgraded outcome (e.g. no verdict +
W0503 upgraded, or `fuzzed(k)` with the real executed count, which the harness
already tracks).

### D5 — `M0601` (mutate timeout) is dead code, and the cargo-mutants invocation has no wall-clock cap

**Claimed** (m4-findings): new diagnostic codes include "`M0601` (mutate timeout)";
§5.4c: "every engine invocation carries a hard cap … Exceeding it yields `timeout`,
never a silent hang".

**Actually true**: `MutantsRunOutcome::Timeout` is declared and matched in
`verify::run_mutate_check` but **never constructed** — `mutants::run` returns only
`ToolError` or `Completed` (checked by grep; the only `Timeout` occurrences are the
declaration and the match arm). `-t <secs>` caps each mutant's *test* phase inside
cargo-mutants; the invocation itself is not wrapped in `timeout` the way the fuzz and
Kani adapters' are, so a hung baseline build or tree copy hangs `verify` silently —
the exact outcome §5.4c's MUST forbids. Additionally, mutants whose tests time out
land in `timeout.txt` and do **not** block `all_caught()`, so a fn can earn
`·spec-strong` with timed-out (uncaught) mutants; defensible as cargo-mutants' own
convention, but undocumented here.

**Cost to fix**: wrap the invocation in `timeout` like the sibling adapters and
construct `Timeout` on exit code 124 (also fixes M0601's wording, which currently
says "within {timeout}s per mutant" for what would be a whole-run cap).

### D6 — a `violation` verdict can be emitted with no witness at all (marker-parse failure path)

**Claimed**: §5.4c MUST — "MUST NOT emit a `violation` without a witness".

**Actually true**: in `run_fuzz_and_test_checks`, when the fuzz test failed but
`parse_fuzz_marker` finds no marker, `render_fuzz_violation` correctly returns an
X0901 tool-error diagnostic with **no** counterexample — but the caller then pushes
`fuzz_label = "violation"` unconditionally, so the node's verdict is `violation`
backed only by a tool error. The right label for that branch is `tool_error`.
Unreached by any fixture (the marker is printed by the same code that fails the
test), but it is a coded violation of a MUST, and the marker pipeline has already
had one real parsing bug this session.

**Cost to fix**: two lines (set the label from `render_fuzz_violation`'s outcome).

### D7 — `W0541`'s wording is false for the exact case that triggers it

**Claimed** (diagnostic text, m4-findings, fuzz_gen/fuzz.rs doc comments): "a
`Vec`/`BTreeSet` of anything but `u8` has no renderer yet".

**Actually true**: `decode_marker_fields` returns `None` for **every** `BTreeSet`,
including `BTreeSet<u8>` — the milestone's own headline shape. My seeded-bug probe on
the `btreeset` shape produced exactly this diagnostic, telling a user whose type *is*
`BTreeSet<u8>` that the problem is types "other than u8". Fails the newbie bar by
being wrong, not just unclear. m4-findings' description of the code (line ~70)
repeats the same error. Side observation from the same probe: the contract text in
the diagnostic renders untidied (`xs . len () as u32`) — `tidy_contract_text` is too
narrow for method calls; cosmetic, M3-inherited.

**Cost to fix**: reword ("a `Vec` of a non-`u8` scalar, or any `BTreeSet`, has no
renderer yet"), one exact-string test.

### D8 — four in-tree doc comments still assert claims this same commit falsified

CLAUDE.md: "when behaviour changes, the artifact describing it changes in the same
commit." Left standing in `2520f8b`:

- `harness_crate.rs` module doc, item 3: "`engines::mutants` must always pass
  [`--gitignore false`] explicitly" — the adapter now must never pass it (clap rejects
  the combination; verified live).
- `engines/mutants.rs` module doc's mechanism block still displays the
  `--gitignore false` command as "the real mechanism" before falsifying it below.
- `engines/fuzz.rs` `HarnessTestRun::failed_tests` field doc: "extracted from …
  `---- <name> stdout ----` failure-detail headers — present regardless of
  `--nocapture`" — the exact claim finding 3 falsified; the parser below it says the
  opposite.
- `engines/mutants.rs` `fn_regex` doc: "Ply always anchors this to one function
  name" — finding 4 is that anchoring matches zero mutants and the code is

- (minor) `harness_crate::write_harness_cargo_toml` doc describes a

prose the implementing session owns, and fixing docs wholesale is beyond this
review's one-trivial-fix budget; they should go in the follow-up commit with D1.

## Overstatements (true, but claimed too strongly)

### O1 — Task 0's formula is shape-*scoped*, but its constants are fitted, not "derived"

The genuinely derived part: only `Vec`-typed harnesses scale (correct — within the
implemented §5.4b subset, `Vec` is the only shape with the measured CBMC unwind
cost), scalar stays 60s, explicit `--engine-timeout` always wins, and the K0601
diagnostic is genuinely good (names the cause, carries three concrete `fixes`,
including "switch to fuzz(256)"). But `verify.rs`'s doc claims "solving
`150 = base + rate * 8` … gives `base = 30, rate = 15`" — one equation, two
unknowns; nothing distinguishes 30+15k from 0+18.75k or 60+11.25k. And the anchor
value 150 is not a measured requirement: it is the M3 e2e's *generous* constant,
while M3 finding 3 measured the identical harness at **~1s to ~107s** across runs —
variance that dominates any k-linear model. §6's amended text is more honest ("a
formula chosen to reproduce the M3 e2e suite's own working value exactly") than the
code comment. Finally, the new default is exercised only by a unit test on the
formula: every e2e still passes an explicit `--engine-timeout` (vecbound still
passes 150), so no test observes the default in real use. Verdict on the brief's
question: not "a bigger magic number wearing a rationale" — the shape split is real
and the diagnostic meets §8 — but the "derived, not guessed" framing overstates two
chosen constants.

### O2 — "shrunk to a minimal cex" is not demonstrated by the fixture that claims it

`fuzzbug`'s seeded bug fails at exactly one input (`x == 7`), so *any* found failure
is already minimal — the e2e's assertion "proptest must shrink to the minimal seeded
input" passes identically with shrinking disabled. The shrinking machinery does work:
my two-parameter probe shrank the irrelevant parameter to 0 (`z=0, a=5`). So the
capability is real but the acceptance fixture cannot detect its loss. A fixture where
a *range* fails (e.g. `x > 7` all failing, expect exactly 8) would pin it.

### O3 — "every M4 non-result diagnostic now carries at least one concrete `Fix`" — not every

True for K0601 (3), E0504 (2), P0601, M0601 (unfireable, see D5), shape-V0505, and
weak-spec W0502. Empty `fixes` on: the no-`ensures` V0505, R0601, both W0110 skip
paths (missing engine names its install command only in the mutate case; the
prove-missing one has none), and the no-viable-mutants W0502. §8 says SHOULD, so
this is an overstatement in the findings, not a spec violation.

### O4 — the `btreeset` acceptance is genuine in shape but weaker in oracle than "This is the point of the whole milestone. Green." suggests

The shape is genuinely Kani-excluded — `BTreeSet<u8>` fails `is_bounded_supported`
(pinned by unit test), matches §5.4b's measured exclusion, no `ply_generated.rs` is
written (asserted), and the default route lands on `fuzz(256)` with no `checks:` key
(asserted). All real. But the fixture's contract (`*result == xs.len()`) is a
tautology of its body, so the fuzz check *cannot* fail on it — and given D1, the e2e's
`fuzzed(256)` + zero-diagnostics assertions would also pass if the harness never
compiled. The repo's own suite therefore never demonstrates that a violation on the
Kani-excluded shape is catchable; m4-findings honestly lists exactly that (W0541
against a real failing case) as NOT RUN. **I ran it**: seeded
`+ if xs.contains(&3) { 1 } else { 0 }` into the fixture body — real run reports
`verdict: violation`, W0541 witness-only with the shrunk minimal witness
`xs = "[3]"`, exit 1. So the milestone's core claim survives adversarial probing;
the acceptance test just doesn't carry the weight by itself. A follow-up fixture
(BTreeSet violation → W0541) would close both this and m4-findings' NOT RUN item.

### O5 — evidence-honesty MUSTs: tested for Kani, mostly only *coded* for the new engines

Timeout-never-violation is genuinely tested end-to-end for the Kani path (M3's
timeout fixture, still green). For the M4 engines it is coded (P0601/R0601 branches)
but untested — no fixture times out under proptest — and unreachable for mutate
(D5). No-violation-without-witness holds on every exercised path (P0502 carries
inputs + rendered test; W0541 carries raw inputs — verified live) but is violated on
the coded marker-parse-failure path (D6). §5.4c's "MUST carry the distinguishing
engine output into the diagnostic" is met by no adapter: every new diagnostic drops
`raw_output` (`let _ = raw_output;`) — an M3-inherited pattern, replicated rather
than worsened.

## Confirmed sound (checked, not taken on trust)

- **The `--copy-target` falsification is real, on all three counts** — verified
  independently against the installed cargo-mutants 27.1.0 source, not the findings'
  quotes: `copy_tree.rs` lines 94–111 contain the unconditional top-level-`target`
  prune gated only by `copy_target`; `options.rs` line 734 has
  `gitignore_off_by_default` and line 359 defaults it off; both flags share the
  `copy_opts` clap group, and running
  `cargo mutants --gitignore false --copy-target true --list` live reproduces the
  exact mutual-exclusion error the findings quote. The spike's `harness-genloc`
  depth analysis (one level too deep to hit the prune) also checks out against the
  spike doc. §5.4c's amendment is accurate, names its artifacts, and its honest-cost
  paragraph is real. This is the strongest work in the milestone.
- **`contract_rt` is genuinely reused, not duplicated** — the whole M4 diff to
  `contract_rt.rs` is `fn widen` → `pub(crate) fn widen`; both K0502 and P0502 paths
  call the same `render_cex_test`, and my probes' rendered tests came through it
  (correct by-name decoding, widened arithmetic). The overflow/widening trap exists
  once.
- **The two-gate split is honest** — `is_fuzz_supported` is strictly broader by
  construction, pinned by unit tests for exactly the asymmetries that matter
  (BTreeSet and `Vec<i32>` fuzz-only, `VecU8` both); routing to `bounded` can still
  time out, but §5.4c explicitly owns that ("checkability is a property of the
  body") and the K0601 outcome is cheap and well-explained. Routing never claims
  `bounded` evidence for a fuzzed shape.
- **The fail-open parser fix is load-bearing and its test catches regression** — I
  re-introduced the bug (`parse_failed_test_names` returning empty) and the
  `fuzzbug` e2e went red at the verdict assertion in 11.7s; reverted, green again
  (both runs recorded above). W0502's wording carries the equivalent-mutant caveat
  and it is exact-string-asserted in the weakspec e2e, including the "not every
  entry below is necessarily a gap to close" sentence — attack point 4 is satisfied.
- **E0504 is a genuine pre-engine refusal** — 0.07s claimed, e2e passes with a 20s
  cap and asserts no harness directory was ever created; both remedies named, both
  in `fixes`.
- **The findings' NOT RUN / scope-cut ledger is honest** — struct fuzzing,
  fuzz-witness persistence, W0541 (now run, by this review), `--re` substring
  over-match, and the prove path are all recorded rather than hidden, and TODO.md
  carries them as unticked items with the same wording.

## Gaps (missing; the unnamed ones)

- **§10's M4 bullet "weak-spec detection (W0502) wired into `worklist`"** — no
  `worklist` command exists in the slice, and this sub-item appears in no scope-cut
  list. Presumably subsumed by the slice's verify-only CLI scope, but it is the one
  M4 bullet neither delivered nor named.
- **`ensure_workspace_member` bails on any crate whose Cargo.toml lacks a

  every standalone crate without the marker. All fixtures carry the table by
  convention, so `fuzz`/`test`/`mutate` currently work only on fixture-shaped
  crates. Recorded nowhere.
- **`mutants.out/` is left in the user's crate root** after every mutate run
  (removed at the *start* of the next run, never after) — outside the `target/ply/`
  housekeeping convention. Minor.
- **`checks: [fuzz(n), test]` on a fn with no `ensures`** silently drops the `test`
  check too (the no-ensures V0505 branch returns before the harness run, examples
  included). Edge case, unrecorded.
- **A missing-engine label (`engine-missing`, from `prove`) beats a passing check in

## Summary answers

**Single most serious finding**: D1 — the fuzz/test adapter fails open on harness
compile errors: an ill-typed user `examples` entry (or any codegen bug) yields
`fuzzed(256)`/`tested` with zero diagnostics. Evidence that lies, on plausible
input, in the milestone whose stated purpose was honest evidence — and it also
hollows out what the `btreeset` acceptance test can prove on its own.

**Does the milestone's core claim hold** (Kani-excluded shape earns real fuzz
evidence)? **Yes.** The shape is genuinely excluded (§5.4b's measured exclusion,
pinned by the gate's unit tests, no Kani harness written), the default routing is
real, and — verified by this review, not by the shipped suite — a seeded violation
on that shape is actually caught, shrunk to a minimal witness, and reported
honestly (W0541, no fabricated rendering, exit 1).

**Acceptance criteria**: 6/6 pass as their tests assert them. Two are weaker
demonstrations than their names claim: the seeded-bug fixture cannot detect loss of
shrinking (O2), and the btreeset fixture's green run cannot by itself distinguish
real fuzzing from a broken harness build (O4/D1). Neither weakness falsifies the
criterion; both deserve follow-up fixtures.

**Is anything in the spec now overclaiming?** Substantively no. §5.4c's mutate
amendment is accurate and independently verified; §6's amendment is candid about
its formula's provenance ("chosen to reproduce"); §10's M4 status names its
artifacts per the generalised D13. Two qualifications: §6's "derives the budget …
rather than guessing" leans harder than the underdetermined fit warrants (the
stronger overclaim — "solving 150 = base + rate·8" — lives in `verify.rs`'s doc
comment, not the spec), and §5.4c's promised high-rejection warning is, in the
shipped code, unreachable below ~100% rejection (D3). The genuinely false claims
this session left standing are in module doc comments (D8), not the spec.
